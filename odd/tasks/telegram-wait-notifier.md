Feature: Telegram notifications for Pi agent waits.
Scope: A standalone, dependency-free Pi extension in `pi-telegram-notifier/`; no interactive remote answers.
Risk: item 2 (Telegram bot credentials and private chat allowlisting).

## Specs

1. S1 — User request: "Quiero crear una nueva extensión, esta me servirá para avisarme cuando un agente que está en ejecución para en espera de mi input." Notify via Telegram when the Pi agent has settled awaiting user input. For the ordinary completed-work notice, do not include agent text; state that it finished and is waiting for user input.
2. S2 — User request: "Quiero que los mensajes se envíen en estas situaciones: 1. Cuando un agente no tienen ningún subagente trabajando y ha terminado su trabajo y está a la espera de un input por parte del usuario." Use final `agent_settled`, not `agent_end`, plus a fresh subagent activity check. Suppress completion notices when a spawner exists but cannot confirm a complete active count of zero; headless child processes must not notify. Use the existing Gentle per-session task snapshot when its publisher is loaded; suppress completion notices when active tasks exist or state is unknown. Pi has no universal registry for other detached subagents; document that limitation.
3. S3 — User request, selected scope: "Solo avisos". Pi replies remain in Pi. Do not claim or implement Telegram answers to Pi dialogs, forms, or questions; an extension cannot resolve another component's blocking UI prompt.
4. S4 — User request: "El token y el ID deben estar almacenados dentro de la extensión en algún fichero propio de la extensión que no sea commitado". Use a local config file within the extension directory; exclude the credentials file from Git. Never place a credential in tracked source, tests, logs, or output. The exposed bot token must not be used; configuration starts empty for a newly rotated token.
5. S5 — User request: "únicamente quiero que se le hable a mi usuario \"@MacDamon15\"." Restrict outbound messages and accepted Telegram updates to the configured, explicitly authorized chat ID; support validating the configured ID against the intended username using Telegram's updates only after a new token is installed. Never broadcast to other chats.
6. S6 — User requested to obtain the chat ID because `/start` was sent. Do not use the exposed token. Provide a safe local setup/diagnostic path using a newly rotated token and verify the Telegram sender username before persisting the chat ID.
7. S7 — User requested form/question buttons, numeric fallback at Telegram message limits, sequential questions, and a completion notice. Superseded in scope by the user's explicit choice "Solo avisos": implement none of these interactive form/answer flows.
8. S8 — Repository convention: extension is self-contained under its own directory, no new runtime dependencies, with tests and README; document installation and restart Pi to load code changes.
9. S9 — User request (verbatim): "Quiero que cuando emitas las notificaciones de Telegram identifiques las sesiones de PI a las que hace referencia con un nombre de sesión, identificando la ruta en la que sucede esa sesión y el nombre de la sesión en el que se está produciend y el tipo de input que se espera por mi parte, si se espera una respuesta a preeguntas realizadas por el agente o si es por trminación de las acciones dle agente". Every notice must carry three fields taken from Pi itself: the session name, the working directory of that session, and the expected input kind, distinguishing "respuesta a preguntas del agente" (UI prompt) from "terminación de las acciones del agente" (settled). Values come from `ctx.sessionManager.getSessionName()` (fallback `sin nombre`) and `ctx.cwd`; a session named or renamed later (`session_info_changed`) uses the current name. Still forbidden in notices: agent text, prompt titles/bodies, and subagent task labels.
